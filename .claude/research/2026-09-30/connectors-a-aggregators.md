**Composio**

- **What it is / license / local deployment:** A managed platform for agent tools, authentication, triggers, and execution. Its public TypeScript and Python SDK repository is MIT licensed. That repository is an SDK, not the complete hosted connector infrastructure. Full self-hosting is an Enterprise arrangement with Helm deployment support; no supported Electron-embedded version of the managed platform was verified. [SDK repository](https://github.com/ComposioHQ/composio), [deployment and custody documentation](https://docs.composio.dev/docs/security/token-custody).
- **OAuth ownership:** Composio supplies shared OAuth applications by default; developers can supply their own OAuth applications and scopes. End users authorize their individual accounts against whichever application is configured. [Authentication](https://docs.composio.dev/docs/authentication).
- **Tokens and data:** In Composio Cloud, Composio stores and refreshes provider tokens and executes provider requests. **Using Jezo’s own OAuth client does not move token storage onto the user’s machine.** Supplying self-managed tokens at execution time avoids Composio storing or refreshing them, but sends them to Composio for execution. [Token custody](https://docs.composio.dev/docs/security/token-custody), [self-managed credentials](https://composio.dev/pricing).
- **Payload retention:** Tool arguments, responses, and trigger payloads are stored by default; execution and trigger logs can remain for up to one year. Paid Zero Data Retention removes covered payload storage, but data still passes through Composio’s execution infrastructure. Attachments can also be staged in temporary object storage. The third party receiving calendar/email contents is **Composio**. [Data retention](https://docs.composio.dev/docs/security/data-retention).
- **Current pricing:** For signups from August 15, 2026: Hobby is $0, with 100,000 tool calls/month, 50,000 trigger events/month, and unlimited connections using your own OAuth app/API keys/MCP. Pro is $29/month with $29 usage credit; additional calls cost $0.0003 and trigger events $0.003. Shared Composio OAuth apps have smaller allowances: 20,000 calls, 10,000 triggers, and 1,000 connections; paid rates are $0.0005/call, $0.005/trigger, and $0.10/additional connection. The connection line does not clearly specify its billing interval. Hobby stops at its caps. [Pricing](https://composio.dev/pricing).
- **Thousands of Jezo users / vendor accounts:** In an embedded deployment, users are represented by Jezo-supplied `user_id` values; they do not each need a Composio developer account. The organization operating that deployment pays its aggregate bill. **(inference)** With developer-owned OAuth apps, 1,000 users averaging 100 calls/month would consume the entire free call allowance. A bring-your-own-Composio-key arrangement would instead require users to manage their own vendor accounts and quotas. [End-user model](https://docs.composio.dev/docs/security/data-retention), [API-key ownership](https://docs.composio.dev/reference/authenticating-to-composio).
- **TypeScript / MCP / coverage:** TypeScript and Python SDKs; hosted session MCP endpoints. Current catalogs list Google Calendar with **50 tools/7 triggers**, Gmail with **62 tools/2 triggers**, and Outlook with **306 tools/5 triggers**. Calendar includes recurring-event instances, free/busy, event CRUD, ACLs, and watch operations; Gmail includes bodies, attachments, drafts, labels, history, and sending. [SDKs](https://github.com/ComposioHQ/composio), [MCP](https://docs.composio.dev/docs/sessions-via-mcp), [Calendar](https://docs.composio.dev/toolkits/googlecalendar), [Gmail](https://docs.composio.dev/toolkits/gmail), [Outlook](https://docs.composio.dev/toolkits/outlook).
- **Lock-in:** Reading connected-account state is explicitly not a supported token-export workflow. **(inference)** Switching execution platforms can therefore require users to reconnect, alongside replacing Composio-specific tool names, sessions, and triggers. MCP standardizes access but does not make those implementations portable. [Credential export boundary](https://docs.composio.dev/docs/security/token-custody).

**Nango — Cloud and self-hosted**

- **What it is / license:** Integration infrastructure for authentication, API proxying, TypeScript actions, syncs, and triggers. The current repository uses **Elastic License 2.0**, which restricts offering substantial functionality as a hosted/managed service and prohibits bypassing license gates. It is source available, not an unrestricted MIT-style dependency, despite the website’s “open source” wording. [Repository](https://github.com/NangoHQ/nango), [actual license](https://github.com/NangoHQ/nango/blob/master/LICENSE).

End users connect through the product’s connection UI; developers operate the Nango account. [Authentication](https://nango.dev/platform/auth), [pricing and app ownership](https://nango.dev/pricing).

However, its API can return access credentials—and optionally refresh tokens—so an application can make provider calls directly. **(inference)** An auth-only deployment can avoid routing email/event payloads through Nango, while still giving Nango custody of OAuth tokens. That still breaks Jezo’s token-locality constraint. [Credential retrieval](https://nango.dev/docs/reference/backend/http-api/connections/get), [proxy requests](https://nango.dev/docs/guides/platform/proxy-requests), [sync record cache](https://nango.dev/docs/guides/functions/syncs/records-cache).

Nango says self-hosted instances do not automatically send telemetry back. [Free self-hosting](https://nango.dev/docs/guides/platform/free-self-hosting).
- **No-Docker desktop suitability:** No library-only edition was verified. Enterprise deployment includes five Node services, PostgreSQL, Redis, object storage, and Elasticsearch. **(inference)** Repackaging this into an automatically managed desktop installation would be substantial infrastructure work, rather than installing its npm SDK. The documented deployments conflict with Jezo’s no-Docker/no-separate-services constraint. [Enterprise architecture](https://nango.dev/docs/guides/platform/self-hosting/self-hosting).
- **Current Cloud pricing:** Free: **10 connections, 10 compute hours/month, 10 GB/month**, hard capped. Pay-as-you-go: **$50/month including $50 credit**, then **$0.29/connection/month**, **$0.72/compute hour**, **$0.50/GB**. A connection is one authorized external account; three users connecting Gmail create three connections. Enterprise discounts and self-hosting are quoted. [Pricing](https://nango.dev/pricing).
- **Thousands of users / vendor accounts:** Standard embedded users do not need Nango accounts; the operator pays for their connections and execution. **(inference)** 1,000 users connecting three accounts each produce $870/month of connection usage at the public rate, before credits, compute, and transfer. Free self-hosting has no Cloud connection bill, but requires operating the stack and respecting its license. [Connection billing](https://nango.dev/pricing), [self-hosting](https://nango.dev/docs/guides/platform/free-self-hosting).
- **TypeScript / MCP / coverage:** TypeScript integration functions and frontend/backend SDKs. Cloud agent sessions expose scoped tools through Streamable HTTP MCP. Gmail, Google Calendar, and Outlook are supported; Outlook currently documents **30 tools and four sync templates**, including message/calendar CRUD and delta-based synchronization. [Agent sessions](https://nango.dev/docs/guides/agent-sessions), [integration catalog](https://nango.dev/api-integrations/), [Outlook implementation surface](https://nango.dev/api-integrations/outlook?category=popular).
- **Lock-in:** Credentials are exportable and integration code is available. **(inference)** This reduces credential lock-in, but functions, scheduling, sync checkpoints, caches, and operational behavior remain coupled to Nango’s runtime. Free self-hosting cannot simply replace the complete Cloud feature set. [Credential export](https://nango.dev/docs/reference/backend/http-api/connections/get), [edition differences](https://nango.dev/docs/guides/platform/free-self-hosting).

Free signup is advertised, but I could not verify current connection/call allowances or production overage rates. Embedded APIs use a developer namespace and user-associated connection metadata; **(inference)** the namespace operator would bear any gateway charges unless users operated their own accounts. Provider-server charges can be additional. [Pricing page](https://smithery.ai/pricing), [multi-user setup](https://smithery.ai/docs/use/connect), [free signup announcement](https://www.arcade.dev/blog/smithery-joins-arcade/).
- **TypeScript / MCP / coverage:** TypeScript SDK integration and generated per-server typed SDKs are documented; generated SDKs are in preview. Calendar/Gmail/Microsoft capability and maintenance quality depend on the particular listed server, not on one uniform Smithery connector implementation. [SDK and server-specific configuration](https://smithery.ai/docs/use/connect).
- **Other registries:** The **Official MCP Registry** is a discovery service listing MCP servers, packages, and remote endpoints. It is not an OAuth aggregator or provider-data proxy. **(inference)** Merely discovering a server there does not transmit mailbox contents or tokens to the registry; using the discovered server introduces that server’s own terms and data flow. [Official registry](https://registry.modelcontextprotocol.io/), [registry source and model](https://github.com/modelcontextprotocol/registry).
- **Lock-in:** **(inference)** Discovery-only usage has little execution lock-in. Smithery Connect adds connection IDs, namespaces, stored authorization, and write-only credentials, making migration materially different. [Connection lifecycle](https://smithery.ai/docs/use/connect).

**Activepieces**

- **What it is / license:** An automation platform whose connectors—“pieces”—are TypeScript/npm packages. The community/core code and pieces are **MIT**, while designated Enterprise directories have a separate license. This is one of the more concrete reusable connector-code collections in the requested list. [License boundaries](https://github.com/activepieces/activepieces/blob/main/LICENSE), [piece packaging](https://www.activepieces.com/docs/admin-guide/guides/manage-pieces).
- **No-Docker possibilities:** Supported installation guides emphasize Docker/Compose or Kubernetes. However, current configuration supports **embedded PGlite** and **in-process Redis emulation**, plus combined app/worker operation. **(inference)** A Jezo-managed sidecar built from source is plausible without separately deployed databases, but a supported desktop bundle was not verified. Extracting selected pieces is a different, smaller undertaking. [Installation](https://www.activepieces.com/docs/install/overview), [runtime configuration](https://www.activepieces.com/docs/install/reference/environment-variables).
- **OAuth ownership:** Shared Activepieces OAuth apps are enabled by default, including through `AP_CLOUD_AUTH_ENABLED` in self-hosted configuration. The platform UI for replacing them with your own apps is a **paid feature**. **(inference)** Self-hosting alone therefore does not prove local OAuth; using extracted MIT pieces with Jezo-managed authorization avoids dependence on that hosted path, but Jezo must supply the lifecycle. [OAuth defaults](https://www.activepieces.com/docs/install/reference/environment-variables), [paid OAuth override](https://www.activepieces.com/docs/admin-guide/guides/manage-oauth2).
- **Tokens and data:** Activepieces stores encrypted connection credentials. Cloud execution processes contents on **Activepieces** infrastructure. Source-based local execution can keep credentials and API calls local, provided hosted OAuth and other remote processing features are excluded. **(inference)** The default shared OAuth path means strict token locality must be verified rather than assumed. [Credential practices](https://www.activepieces.com/docs/admin-guide/security/practices), [hosted OAuth switch](https://www.activepieces.com/docs/install/reference/environment-variables).
- **Current pricing:** Free Cloud: **1,000 credits/month**; Plus **$20/month/10,000 credits**, Team **$200/month/50,000 credits**; additional credits **$0.007**. A flow run costs one credit, agentic actions one each, with separate AI multipliers. **Embed starts at $36,000/year**, sized by customers and usage. Community Edition is free self-hosted. The pricing page contradicts itself about whether Free credits reset daily or monthly, so that behavior remains unresolved. [Pricing](https://www.activepieces.com/pricing), [Embed commercial model](https://www.activepieces.com/embed).
- **Thousands of users / accounts:** The commercial Embed product provisions users through the developer’s signed JWT; users do not separately sign up. The operator pays its contract. **(inference)** Reusing MIT piece source locally has no per-user vendor fee, but is not the same product as purchasing the Enterprise Embed SDK. [Embedded identity](https://www.activepieces.com/embed), [MIT boundary](https://github.com/activepieces/activepieces/blob/main/LICENSE).
- **TypeScript / MCP / coverage:** Pieces are TypeScript; the platform has MCP support. Google Calendar source includes CRUD, availability, recurring instances, and custom API calls. Gmail currently lists **11 actions/4 triggers**, Outlook Mail **12/3**, and Outlook Calendar only **four actions/no triggers**—create, delete, list, and custom API call. The latter is a concrete coverage gap for calendar synchronization. [Calendar source](https://github.com/activepieces/activepieces/blob/main/packages/pieces/community/google-calendar/src/index.ts), [Gmail](https://www.activepieces.com/pieces/gmail), [Outlook Mail](https://www.activepieces.com/pieces/microsoft-outlook), [Outlook Calendar](https://www.activepieces.com/pieces/microsoft-outlook-calendar), [MCP](https://www.activepieces.com/docs/mcp/overview).
- **Lock-in:** **(inference)** MIT pieces can be adapted or maintained independently. Their action contexts, dynamic properties, triggers, and connection assumptions still require a compatibility layer; importing the whole platform introduces its workflow/database model. [Piece source structure](https://github.com/activepieces/activepieces/blob/main/packages/pieces/community/google-calendar/src/index.ts).

**n8n as a connector library**

- **What it is / license:** A workflow platform with TypeScript connector nodes. Its code is distributed under **Sustainable Use License**, with Enterprise portions separately licensed. The license permits personal/noncommercial use and internal business use, but limits distribution to free noncommercial purposes. It is not an unrestricted open-source connector library. [Actual license](https://github.com/n8n-io/n8n/blob/master/LICENSE.md).
- **No-Docker execution:** Its npm installation documentation supports local Node execution, but now states **npm-based installs are deprecated from n8n 3.0**. **(inference)** An older/version-pinned bundled runtime is technically possible, but relying on it as a maintained desktop distribution path is uncertain. [Current npm documentation](https://docs.n8n.io/deploy/host-n8n/install-options/install-with-npm).
- **Library reuse:** The Google Calendar node implements `INodeType` and executes against n8n’s `IExecuteFunctions`, credential helpers, parameters, input items, and timezone context. **(inference)** Its nodes are not ordinary independent API-client functions; extracting them requires reproducing engine interfaces or rewriting the connector. [Calendar implementation](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Google/Calendar/GoogleCalendar.node.ts).
- **OAuth ownership / tokens / data:** n8n Cloud provides managed Google OAuth; self-hosted installations require a custom OAuth client. n8n encrypts credentials in its database. Local self-hosted provider calls can avoid **n8n Cloud**; cloud workflows place credentials and processed data on n8n infrastructure. [Google OAuth](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-single-service), [credential encryption](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key), [hosting/data location](https://n8n.io/pricing/).
- **Current pricing:** Community Edition is free self-hosted under its license. Cloud Starter is **€20/month billed annually/2,500 workflow executions**; Pro **€50/month/10,000 executions**. Self-hosted Business is **€667/month billed annually/40,000 executions**. Enterprise and product embedding are contractual. Billing is by workflow execution, not by every node or connected account. [Pricing](https://n8n.io/pricing/), [embedding license guidance](https://support.n8n.io/article/can-i-use-your-license-for-my-use-case).
- **Thousands of users / accounts:** Local personal instances need no n8n Cloud account or per-connection subscription. Hosted/product-embedded deployments have different licensing rules. **(inference)** Free noncommercial Jezo distribution may fit permitted use, but the n8n portion cannot be relicensed MIT, and downstream commercial forks would not inherit unrestricted rights. Do not apply SaaS credential-hosting rules indiscriminately to a user’s personal local instance. [License](https://github.com/n8n-io/n8n/blob/master/LICENSE.md), [vendor embedding guidance](https://support.n8n.io/article/can-i-use-your-license-for-my-use-case).
- **TypeScript / MCP / coverage:** TypeScript nodes; MCP Server Trigger can expose connected tools. Google Calendar handles availability, CRUD, attendees, notifications, and recurrence. Gmail and Microsoft Outlook are built-in nodes; Outlook documents mail and calendar operations. [Calendar source](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Google/Calendar/GoogleCalendar.node.ts), [Google nodes](https://docs.n8n.io/integrations/builtin/credentials/google/oauth-single-service), [Outlook](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.microsoftoutlook), [MCP trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger).
- **Lock-in:** **(inference)** Source is inspectable, but licensing, engine interfaces, credentials, expressions, and workflow formats make it less portable than its npm packaging suggests. [Node implementation](https://github.com/n8n-io/n8n/blob/master/packages/nodes-base/nodes/Google/Calendar/GoogleCalendar.node.ts), [license](https://github.com/n8n-io/n8n/blob/master/LICENSE.md).

**Additional 2026 development: One, formerly Pica**

- **Why it matters:** Pica became **One on March 25, 2026**; a hosted OAuth-authenticated MCP endpoint followed on July 13. Its distinguishing proposition is connections owned by each end user’s One account, rather than solely by an embedding developer’s project. [2026 changelog](https://www.withone.ai/changelog).
- **License / deployment:** The current TypeScript `@withone/connect` SDK is **GPL-3.0**. The platform itself is hosted. Its connector knowledge uses a separate **One Knowledge Commons License**, with attribution, anti-extraction, share-alike, and some commercial licensing conditions; it is not MIT-style material. No complete local runtime was verified. [SDK license](https://github.com/withoneai/connect), [knowledge license](https://www.withone.ai/licenses/knowledge), [platform description](https://www.withone.ai/).
- **OAuth / tokens / data:** One stores provider credentials encrypted and attaches them server-side. The application stores a separate One authorization grant/token. **Actual provider traffic follows agent → One → provider → One → agent.** Thus **One Systems** receives credentials and processes calendar/email contents, even though it says contents are not retained. Developer-owned OAuth applications were documented in legacy Pica AuthKit, but the current public pages do not establish availability for every connector. [Explicit data-flow diagram](https://www.withone.ai/enterprise/security), [grant token storage](https://github.com/withoneai/connect), [legacy custom-app support](https://docs.picaos.com/authkit/management).
- **Current pricing:** Free: **1 million requests/month, 20 requests/minute, one organization/project**. Starter: **$29/month, 100 requests/minute**, 20 organizations/projects. Pro: **$199/month, 500 requests/minute**, 100 organizations/projects. Public plans show the same monthly request allowance; excess rate returns `429`, with no usage overage bill. Limits are per account across its keys. [Pricing](https://www.withone.ai/pricing).
- **Thousands of users / vendor accounts:** One advertises Connect as free to embed and free for users, but users connect in **their own One account**. **(inference)** That potentially avoids a maintainer-funded per-connection bill, while introducing mandatory vendor identity and hosted token custody. The documented SDK still expects confidential backend routes and a client secret; a supported public-client desktop flow was not verified. [User pricing](https://www.withone.ai/pricing), [integration requirements](https://github.com/withoneai/connect).
- **TypeScript / MCP / coverage / lock-in:** TypeScript Connect SDK, CLI, and hosted MCP. Gmail and Google Calendar are explicit examples; current Microsoft calendar/mail completeness was not independently verified. **(inference)** Grants, action IDs, hosted execution, and proprietary knowledge conditions create lock-in despite its standard OAuth/MCP interfaces. [Connect](https://www.withone.ai/products/connect), [MCP launch](https://www.withone.ai/changelog), [knowledge terms](https://www.withone.ai/licenses/knowledge).

**Additional local option: Google Workspace CLI (`gws`)**

- **What it provides:** An **Apache-2.0**, Rust-based CLI distributed as binaries and through `@googleworkspace/cli`. It generates commands from Google Discovery documents and covers Gmail, Calendar, Drive, and other Workspace APIs. It is explicitly **not an officially supported Google product**. [Current repository](https://github.com/googleworkspace/cli).
- **OAuth / locality / pricing:** It accepts a Desktop OAuth client, stores credentials locally with OS-keyring-backed encryption, and calls Google directly. It has no connector-vendor account or per-connection charge. **(inference)** It can use a supplied developer-owned client or an end user’s client; registration, scopes, and provider quotas still belong to that OAuth project. [Authentication and configuration](https://github.com/googleworkspace/cli/blob/main/README.md).
- **Current gaps:** It is a CLI/sidecar, not a TypeScript connector SDK, and only covers Google. Its changelog says **MCP mode was removed in 0.8.0** and built-in multi-account selection was removed in 0.7.0. Separate configuration directories provide an application-managed isolation mechanism, but a multi-account desktop product needs its own coordination. **(inference)** Google OAuth verification and Jezo’s GUI onboarding remain application work. [Current changelog](https://github.com/googleworkspace/cli/blob/main/CHANGELOG.md), [configuration directories](https://github.com/googleworkspace/cli/blob/main/README.md).
- **Privacy qualification:** Optional response sanitization invokes **Google Cloud Model Armor**, sending responses to that additional service. Ordinary direct API execution does not require enabling it. [Optional Model Armor integration](https://github.com/googleworkspace/cli/blob/main/README.md).

**Are there fully local, library-only aggregators?**

**No turnkey, broad equivalent of the hosted platforms was verified that combines managed OAuth, token refresh, a maintained action catalog, and Electron-ready packaging while keeping both provider tokens and payloads exclusively on the user’s machine.** The available local options split those responsibilities:

| Local option | What can remain local | Main gap |
|---|---|---|
| **Activepieces MIT pieces** | Selected connector code and direct provider calls | **(inference)** Jezo must supply action context, authorization, token lifecycle, scheduling, and packaging. [Piece source](https://github.com/activepieces/activepieces/blob/main/packages/pieces/community/google-calendar/src/index.ts) |
| **`agent.pw`, MIT** | Embeddable credential vault, PKCE, refresh, revocation | Auth infrastructure, not calendar/mail tools. Requires a PostgreSQL-compatible database; its tests use in-memory PGlite, but persistent desktop packaging was not verified. [Repository](https://github.com/clavia-labs/agent.pw), [architecture](https://github.com/clavia-labs/agent.pw/blob/main/docs/architecture.md) |
| **Grant, MIT** | Node OAuth middleware with configurations for 200+ providers | OAuth handshake/configuration rather than mail/calendar action wrappers or a complete persistent token-management product. **(inference)** Suitable as local building material, not a complete aggregator. [Repository](https://github.com/simov/grant) |
| **Standalone Arcade framework** | Python tools executed locally with supplied tokens | Managed OAuth belongs to the separate platform; obtaining and maintaining tokens becomes application work. [Standalone mode](https://github.com/ArcadeAI/arcade-mcp) |
| **Selected Klavis servers / Open Strata** | Local server execution and tool routing | Per-server packaging and auth behavior; managed OAuth still calls Klavis. Docker examples cannot be assumed to establish vendor-free operation. [Repository](https://github.com/Klavis-AI/klavis), [manual-token example](https://www.klavis.ai/docs/mcp-server/notion) |
| **`gws`, Apache-2.0** | Google tokens, connector execution, and credential files | Google only; CLI rather than TypeScript library; current MCP and built-in multi-account support removed. | **Personal local n8n** | Credentials and workflow execution | Restricted license, engine coupling, and deprecated npm distribution path; not an unrestricted connector library. [License](https://github.com/n8n-io/n8n/blob/master/LICENSE.md), [npm status](https://docs.n8n.io/deploy/host-n8n/install-options/install-with-npm) |

For `agent.pw`, the documented library has **no required daemon, proxy, or second server hop**. **(inference)** Using an embedded compatible database could make its auth layer fully local, but it would still need provider profiles and connector implementations. It does not magically provide Google Calendar/Gmail/Microsoft coverage. [Architecture](https://github.com/clavia-labs/agent.pw/blob/main/docs/architecture.md).

**Trade-offs that materially affect Jezo**

- **OAuth application ownership and token custody are independent.** A vendor can use Jezo’s OAuth application while still storing every user’s refresh token. Composio explicitly documents this; Paragon’s end-user-client flow likewise stores resulting credentials. [Composio](https://docs.composio.dev/docs/security/token-custody), [Paragon](https://docs.useparagon.com/resources/user-configured-oauth).
- **“Self-hosted MCP” can mean only a local adapter.** Paragon’s adapter still calls hosted ActionKit; Arcade’s standalone framework and complete managed platform are different deployments. **(inference)** A localhost MCP endpoint is insufficient evidence of local data handling. [Paragon adapter](https://github.com/useparagon/paragon-mcp), [Arcade framework](https://github.com/ArcadeAI/arcade-mcp).
- **“No data stored” is weaker than Jezo’s privacy constraint.** One’s diagram explicitly returns results through One; Composio’s retention controls leave execution processing in place. **(inference)** A local model does not change either connector data path. [One](https://www.withone.ai/enterprise/security), [Composio](https://docs.composio.dev/docs/security/data-retention).
- **A maintainer-owned hosted project usually assumes a trusted backend.** Merge explicitly requires protecting its organization key and minting user-scoped credentials; Nango sessions are created by a backend. **(inference)** Shipping an unrestricted shared project secret inside every Electron installation would expose cross-user capabilities and shared billing. Per-user vendor accounts or a provisioning broker change that trade-off; neither follows automatically from installing an SDK. [Merge](https://docs.merge.dev/merge-agent-handler/setup/building-an-agent), [Nango](https://nango.dev/docs/guides/agent-sessions).
- **MCP and CLI access do not provide Jezo’s workspace representation.** These products expose operations, credentials, or workflows. **(inference)** Persisting calendar/email-derived state into Jezo’s directory, handling stale state after an absence, and checking consequential exits remain Jezo responsibilities. A broad tool catalog does not settle those product requirements. [Composio tool model](https://docs.composio.dev/toolkits/googlecalendar), [Nango synchronization model](https://nango.dev/docs/guides/functions/syncs/records-cache).
- **Vendor guardrails are not automatically Jezo’s trust model.** Merge scans calls for data patterns, while One enforces granted actions. **(inference)** These controls can help constrain exits, but neither establishes whether an action reflects the owner’s intent after an email has steered the agent. [Merge security gateway](https://docs.merge.dev/merge-agent-handler/overview), [One runtime enforcement](https://www.withone.ai/enterprise/security).

**Verification limits:** Sources checked September 30, 2026. Unless explicitly marked October 2025, links above refer to live documentation/current repository heads; many pages are undated. Coverage means documented operations or inspected source, not an executed reliability benchmark. Current Klavis and Smithery pricing, Pipedream’s base subscription price, and several desktop-packaging paths remain explicitly unverified.
