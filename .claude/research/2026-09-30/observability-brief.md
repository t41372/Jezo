# Brief: observability for Jezo's agent, to debug and improve long-term memory

Read-only research. Do not change any files. You may read the repository (AGENTS.md, docs/design/memory.md, docs/design/backend.md, packages/pi-memory/src/*, src/main/agent/host.ts) and research on the web. Today is 2026-09-30.

## Context
Jezo is an open-source, local-first Electron + TypeScript desktop app for managing a life (todos, goals, calendar, habits, memory). Its embedded agent is the pi coding agent SDK (npm `@earendil-works/pi-coding-agent`, version 0.99.x), running in Electron's main process. Models are local (LM Studio, Ollama) or any cloud provider the user adds. pi saves each conversation as a JSONL session file in the workspace (messages, tool calls, results, model, thinking level). Long-term memory is our own pi extension (`packages/pi-memory`): memory_remember / memory_recall / memory_forget tools, a budgeted memory section added to the system prompt at `before_agent_start`, FTS5 trigram recall, supersede via `replaces`, tombstones for forgotten memories, and a new check that holds back a save that looks related to an existing memory until the agent says whether it replaces it.

What the maintainer wants: to look at agent traces to debug and optimize long-term memory. Examples of questions he needs answered: what was in the memory section of the prompt for this run; which memories were recalled and which were used; why the model didn't pass `replaces` (a real model left it out two runs in three); which saves were held back or refused and what the agent did next; how token cost and latency change with the memory budget; comparing two versions of the memory prompt or policy over the same set of conversations (evals / regression tests); replaying a session against a different model.

Constraints:
- Privacy is central: traces contain the user's life. Anything that sends traces to a third party's cloud must be called out, and opt-in only.
- For end users: nothing that needs Docker or a separately deployed service. For the maintainer's own development, a local tool that needs Docker or a local server may be acceptable, but say which is which.
- Prefer open-source; say the license.

At least: Langfuse, Arize Phoenix, Laminar, Opik (Comet), Helicone, LangSmith, W&B Weave, Braintrust, Logfire (Pydantic), AgentOps, OpenLLMetry/Traceloop, OpenLIT, Lunary, HoneyHive, Galileo, Agenta, Promptfoo (evals), Inspect (UK AISI), plus plain OpenTelemetry backends usable locally (Jaeger, Grafana Tempo, SigNoz, otel-tui, otel-desktop-viewer), and anything 2026-new that matters. Also: does pi have its own tracing, OpenTelemetry integration, session viewers, or community extensions for this (search pi.dev packages, the pi repo, its docs)? Do Hermes Agent, OpenClaw, Letta, Claude Code or Codex expose agent traces, and how?
2. **Memory-specific debugging and evaluation**: how people evaluate and debug long-term memory systems in 2026 (LongMemEval, LoCoMo, MemoryAgentBench, BEAM, HorizonBench, and newer), which tools support memory-specific views (what was retrieved vs used, write decisions, supersede/forget), and what a small, realistic eval set for Jezo's memory could look like (scenarios, scoring, how to run it with local models).
3. **Options for Jezo**, compared: (a) instrument with OpenTelemetry GenAI spans and point at a local backend; (b) adopt one tool's SDK directly; (c) build a small trace view on pi's own session JSONL plus a few extra events (memory section contents, recall results, held-back saves) written by our extension, possibly as a developer page in the app; (d) combinations. For each: effort, what it shows, privacy, and how it helps the concrete questions above.
4. **Your recommendation**, with the first concrete steps, and what the maintainer would need to install or run.
