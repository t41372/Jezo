## 1. Wider landscape

Research date: **2026-09-30**. Prices below are USD unless stated otherwise. Sources explicitly dated before 2026 are marked. Undated documentation was read live; its original publication date is unknown. **“Not verified” means the public sources reviewed did not establish the detail.** Fit assessments are marked **(inference)**.

Three distinctions matter throughout this survey:

- **An open-source SDK does not establish an open-source connector backend.** Metorial, for example, licenses its catalog under Apache 2.0 but its platform under FSL-1.1-ALv2. [Catalog](https://github.com/metorial/metorial), [platform license](https://github.com/metorial/metorial-platform/blob/dev/LICENSE).
- **“We do not store your data” can still mean “your data passes through our servers.”** Unified.to and Knit explicitly describe that arrangement. [Unified.to security](https://unified.to/security), [Knit security](https://getknit.dev/security/).
- **An OAuth broker need not carry calendar or email content.** WorkOS Pipes returns provider access tokens so the application can call the provider directly; the refresh tokens nevertheless remain in WorkOS’s cloud. [Pipes](https://workos.com/pipes).

This is a broad survey of the requested families and additional relevant services, rather than a claim that every small integration vendor has been found. The aggregators assigned to the other researchers are omitted as standalone entries; they appear below only where needed to explain a project’s documented choice.

### Google, Microsoft and OpenAI’s own offerings

**Google’s official remote Workspace MCP servers are now a real alternative interface.** The September 2026 documentation lists Gmail, Calendar, Drive, Docs, Sheets, Slides, Chat and People servers, in **Developer Preview**. Each product has a dedicated endpoint and requires Google Cloud/OAuth setup. Calendar uses `https://calendarmcp.googleapis.com/mcp/v1`. The published examples configure customer-created OAuth clients. [Workspace setup](https://developers.google.com/workspace/guides/configure-mcp-servers), [Calendar setup](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server).

**(inference)** A local client talking directly to Google’s server need not introduce an additional connector company. It does not, however, remove Google registration, quota ownership, preview eligibility or the choice of where model inference happens.

There is also a trust-model qualification: Google’s Calendar MCP documentation says prompts and responses must be screened for malicious content/prompt injection, using Model Armor or a documented alternative. That differs from Jezo’s stated emphasis on checking exits. Whether an exits-focused implementation satisfies the published requirement was **not established**. [Calendar security requirement](https://developers.google.com/workspace/calendar/api/guides/configure-mcp-server).

Google separately offers **Agent Identity auth manager**, a Google-managed credential vault/broker, plus cloud Integration Connectors. These are hosted infrastructure, distinct from its directly hosted Workspace MCP endpoints. [Auth manager](https://docs.cloud.google.com/iam/docs/auth-manager-overview), [connector configuration](https://docs.cloud.google.com/integration-connectors/docs/connectors/http/configure).

Microsoft has several separate layers:

- **MSAL + Microsoft Graph:** client libraries and direct provider APIs; desktop apps are public clients and can use authorization code with PKCE. [Desktop configuration](https://learn.microsoft.com/en-us/azure/active-directory/develop/scenario-desktop-app-registration), [supported flows/accounts](https://learn.microsoft.com/en-us/entra/identity-platform/authentication-flows-app-scenarios).
- **Work IQ MCP/CLI:** Microsoft-hosted access to Microsoft 365 intelligence and operations. Its current enablement guide requires tenant administrative consent and a **Microsoft 365 Copilot license per user**. This is not equivalent to ordinary personal Outlook access through Graph. [Overview](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/mcp/overview), [requirements](https://github.com/microsoft/work-iq/blob/main/ADMIN-INSTRUCTIONS.md).
- **Copilot Studio, Foundry and Logic Apps:** hosted agent/workflow platforms with connectors and MCP integration. Copilot Studio meters capabilities using credits; Foundry/Logic Apps execute through Azure resources. **(inference)** These break Jezo’s no-deployment/no-paid-infrastructure shape if adopted as its connector runtime. [Billing](https://learn.microsoft.com/en-us/microsoft-copilot-studio/requirements-messages-management), [Foundry + Logic Apps](https://learn.microsoft.com/en-us/azure/logic-apps/automate-foundry-agents-with-workflows).

**OpenAI Apps SDK / ChatGPT apps** is an app ecosystem built around MCP, authentication and ChatGPT experiences. ### Documented reasons, problems and changes

These sources explain actual decisions; other table entries describe implementation without inventing a motive.

1. **Lindy: breadth and maintenance cost.** Its customer statement says it spent **over $1 million building about 250 integrations over two years**, then obtained roughly 2,500 through Pipedream. That is direct evidence of a hosted assistant buying connector breadth after maintaining native integrations. [Customer statement](https://pipedream.com/?via=thomas).

2. **Dust: marketplace approval affected usability.** Before its March 2026 change, a non-approved Slack app caused warnings and could be blocked by company policies. Dust switched its action tool to its approved Marketplace app. [Change explanation](https://docs.dust.tt/changelog/slack-tool-now-uses-official-dust-marketplace-app).

3. **Raycast: public desktop clients cannot protect a shared client secret.** Its OAuth API documentation explicitly grounds PKCE support in that fact. The proxy is provided for providers that do not support the necessary native flow. [OAuth rationale](https://developers.raycast.com/api-reference/oauth).

4. **Notion: hosted OAuth reduced setup friction.** Its **2025** engineering account describes an initial downloadable MCP server requiring users to create integrations and configure keys, followed by a hosted server that manages OAuth sessions and API tokens. It also describes generating tools from OpenAPI schemas. [Engineering account — 2025 source](https://www.notion.com/blog/notions-hosted-mcp-server-an-inside-look).

5. **Perplexity: bought retrieval/connectivity capability.** Its **December 2024** Carbon announcement specifically identifies connecting apps such as Notion and Google Docs as the purpose. [Announcement — 2024 source](https://www.perplexity.ai/nl/hub/blog/welcoming-carbon-to-the-perplexity-team).

6. **Khoj: maintenance outweighed use.** Its data-source documentation says GitHub integration is unmaintained, sees little use and is cumbersome to maintain. [Data-source status](https://docs.khoj.dev/category/data-sources/).

7. **LobeHub: aggregator choice changed in production development.** The June 2026 PR explicitly replaces Klavis with Composio. It documents the replacement and implementation, but does **not establish a cost/privacy rationale** for the change. [Merged PR](https://github.com/lobehub/lobehub/pull/15461).

8. **Agentic: open-source availability did not ensure longevity.** Its February 2026 archival notice says it failed to gain traction and the maintainer moved on. [Notice](https://github.com/transitive-bullshit/agentic).

9. **Google community servers: recurring authorization is a visible support problem.** `google-calendar-mcp` documents weekly expiry for testing-mode apps and a publishing/re-authentication workaround. Google’s official documentation independently confirms the underlying testing limitation. [Community documentation](https://github.com/nspady/google-calendar-mcp), [Google audience rules](https://support.google.com/cloud/answer/15549945?hl=en).

## 3. Patterns actually in use

### Connector approaches and their trade-offs

[Dust](https://docs.dust.tt/changelog/slack-tool-now-uses-official-dust-marketplace-app), [Claude cloud execution](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) | **(inference)** Smooth onboarding is exchanged for cloud custody and vendor-controlled availability. ### OAuth verification, quota and cost are separate problems

**MCP authentication and Google API authorization are not interchangeable.** **(inference)** Successfully authenticating a host to an MCP server does not, by itself, register or verify that server’s Google OAuth application. The community Workspace server explicitly requires a user-owned Google client; Google’s official remote-server examples also require OAuth setup. [Community setup](https://github.com/taylorwilsdon/google_workspace_mcp), [Google setup](https://developers.google.com/workspace/guides/configure-mcp-servers).

Google’s current documentation distinguishes:

- **Testing:** up to **100 test users**; relevant authorizations expire after **seven days**, with limited basic-profile exceptions. [Audience settings](https://support.google.com/cloud/answer/15549945?hl=en).
- **Personal-use exception:** fewer than 100 users can use qualifying personal apps without verification, with warning screens. This is not an exemption for a broadly distributed app merely because each installation runs locally. **(inference)** [Verification exceptions](https://support.google.com/cloud/answer/13464323?hl=en).
- **Restricted scopes:** restricted-scope verification and, when restricted data is accessed from or through third-party servers, an **annual security assessment**. Google does not set the assessor’s fee; current FAQs also describe eligible free Tier 2 assessment paths. [Restricted verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [assessment FAQ](https://support.google.com/cloud/answer/13463817?hl=en).

**(inference)** Sending retrieved Gmail content to a cloud model is a separate data flow from keeping the connector/token store local. A desktop implementation should therefore not be assumed to qualify for every local-only assessment exception merely from its executable format.

There is an important **2026 Calendar quota change**. The September 11 documentation lists new-project limits of **10,000 requests/minute/project**, **600/minute/user/project**, and a **one-million-request daily billing threshold**. Standard use is currently at no additional cost; above-threshold billing is planned with at least 90 days’ notice, and full prices were not published in that page. Projects with qualifying earlier usage retain earlier quotas. [Calendar quotas and planned billing](https://developers.google.com/workspace/calendar/api/guides/quota), [September 2026 standardized model](https://developers.google.com/workspace/tools-safety).

**(inference)** A shared Jezo Google project consequently shares project-level policy and quota consequences across installations. BYO projects distribute those responsibilities but impose onboarding work. Neither arrangement requires calendar content to pass through Jezo-maintainer servers.

Slack supplies another example of provider policy determining connector usefulness. Current docs apply a **one-request/minute** limit to `conversations.history`/`replies` for qualifying new commercially distributed non-Marketplace apps, with 15-result limits; approved Marketplace and internal apps are treated differently. Current docs say existing installations are not subject to the new posted limits, so older blanket descriptions of a 2026 migration should not be copied unquestioningly. [Rate limits](https://docs.slack.dev/apis/web-api/rate-limits/), [history](https://docs.slack.dev/reference/methods/conversations.history/), [replies](https://docs.slack.dev/reference/methods/conversations.replies/).

Slack’s official MCP currently allows **Marketplace-published and internal apps**, prohibits unlisted apps, and documents **confidential OAuth requiring a client secret**. **(inference)** That makes it materially different from a generic desktop PKCE connection to every provider. [Slack MCP](https://docs.slack.dev/ai/slack-mcp-server/).

### Maintenance and security failures observed

**Connector installation is still application maintenance.** A June 2025 Goose Calendar issue records a Python stdio server closing during initialization. A July 2025 AnythingLLM issue records remote server 401 failures where the user expected an OAuth flow. These are historical incident reports, not assertions that the current releases remain broken. [Goose issue — 2025](https://github.com/aaif-goose/goose/issues/3088), [AnythingLLM issue — 2025](https://github.com/Mintplex-Labs/anything-llm/issues/4161).

**Tool descriptions and returned content can steer the model across connectors.** Invariant’s **April 2025** research demonstrated tool-poisoning attacks and followed up with WhatsApp history exfiltration examples. **(inference)** A trustworthy email connector does not make its retrieved messages trustworthy instructions, and a malicious neighboring tool can affect how that email data is used. [Original research — 2025](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks).

**Connector code can be malicious independently of prompt injection.** Postmark’s **September 2025** notice describes an unofficial `postmark-mcp` package that built trust across 15 releases, then secretly added a BCC recipient in version 1.0.16. Postmark explicitly says it was not its package and its legitimate API was unaffected. [Provider incident notice — 2025](https://postmarkapp.com/blog/information-regarding-malicious-postmark-mcp-package).

**Skills are also an executable supply-chain channel.** VirusTotal reported malicious OpenClaw skills in **February 2026**, including malware delivery disguised as automation setup. OpenClaw subsequently announced VirusTotal scanning for ClawHub. Its current security page distinguishes official infrastructure from third-party skills. [VirusTotal research](https://blog.virustotal.com/2026/02/from-automation-to-infection-how.html), [partnership](https://openclaw.ai/blog/virustotal-partnership?trk=article-ssr-frontend-pulse_little-text-block), [current scope](https://openclaw.ai/security).

For Jezo’s specified trust model, two conclusions follow **(inference)**:

- Checking outbound recipients, destinations and irreversible effects addresses the demonstrated **exfiltration/action** problem more directly than assuming OAuth, MCP or a marketplace makes content safe.
- A broker that hides credentials only helps if all relevant exits pass through its enforcement point. Jentic explicitly acknowledges that same-OS-user agents can read credential-holding local state; local token separation alone is not an isolation boundary. [Jentic’s stated boundary](https://github.com/jentic/jentic-one).

The observed landscape therefore contains several independent choices: **who registers the OAuth app, who stores tokens, who executes connector calls, who stores imported content, and who runs model inference**. **(inference)** “Uses MCP,” “has an open-source SDK,” “runs on desktop,” and “does not store data” each answer only part of that set.
