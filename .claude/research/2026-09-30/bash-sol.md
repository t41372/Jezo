**Anthropic’s `@anthropic-ai/sandbox-runtime` is the most direct fit for Jezo’s existing architecture.** It is an ESM Node library and CLI, requires Node ≥20.11, and uses the Apache-2.0 license. The repository’s current package version is **0.0.78**, with that release published on September 30, 2026. It remains labelled a beta research preview; Windows support is labelled alpha. [package metadata](https://github.com/anthropics/sandbox-runtime/blob/main/package.json), [releases](https://github.com/anthropics/sandbox-runtime/releases), [runtime documentation](https://github.com/anthropics/sandbox-runtime)

| Platform | Enforcement | Consequences for Jezo |
|---|---|---|
| macOS | Generates Seatbelt profiles and launches through `sandbox-exec`. Restrictions cover the subprocess tree, including process, filesystem, network and selected IPC operations. [macOS implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/macos-sandbox-utils.ts) | Runs installed macOS binaries directly. No VM image is needed. |
| Linux | Bubblewrap creates filesystem, PID and network namespaces. Host proxies are reached through Unix-socket bridges; seccomp blocks additional Unix-socket creation when its helper is available. [Linux implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/linux-sandbox-utils.ts) | Requires `bwrap`, `socat` and `rg`, plus working user namespaces. Jezo must verify IPC isolation rather than accept a warning about missing seccomp. |
| Windows | A bundled `srt-win.exe` runs commands as a dedicated `srt-sandbox` account, under a restricted token and job object. NTFS ACL entries grant filesystem access; Windows Filtering Platform rules fence outbound connections by that account’s SID. [Windows implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/windows-sandbox-utils.ts) | Requires a one-time elevated installation. This is now a native implementation, rather than merely a recommendation to use WSL. |

The filesystem policy has distinct read and write semantics: reads are broadly permitted unless denied, with `allowRead` reopening selected regions; writes require `allowWrite`, with `denyWrite` carving out protected locations. Consequently, configuring only `allowWrite: [workspace]` does **not** make reads workspace-only. [configuration schema](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/sandbox-config.ts)

For Jezo, denying reads under the owner’s home directory and reopening the workspace, installed tool directories and selected imports is a reasonable default. It addresses credential harvesting and access to unrelated private files after outside content steers the agent. The owner should be able to grant additional folders through the GUI. (inference)

Network filtering uses HTTP/HTTPS and SOCKS5 proxies outside the restricted process. The default configuration denies network destinations; allowed domains can include wildcards and optional ports. The OS boundary prevents a child from simply deleting `HTTPS_PROXY` and connecting directly. A normal HTTPS CONNECT tunnel does not inspect the encrypted request body. [runtime documentation](https://github.com/anthropics/sandbox-runtime), [HTTP proxy implementation](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/http-proxy.ts)

The library lifecycle is straightforward: initialize a policy, wrap commands, launch them, and clean up resources. Current versions expose `wrapWithSandboxArgv()`, returning an argv/environment launch descriptor; Windows requires this API and an outer `spawn(..., { shell: false })`. The manager holds module-global policy and proxy state, so it should not be treated as an independently configurable object per conversation. [manager implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/sandbox-manager.ts)

That global state matters for per-skill policies. Jezo should use a fixed policy per runner process, or serialize policy changes while no commands are active. It should not swap one global network allowlist while commands from several skills are running. LobeHub’s implementation explicitly handles this conflict. (inference) [LobeHub runtime](https://github.com/lobehub/lobehub/blob/canary/packages/device-sandbox/src/runtime.ts)

**SRT has useful newer features for options (d) and (e).** `network.tlsTerminate` experimentally terminates HTTPS inside the host proxy. A library-supplied `filterRequest` receives a web-standard `Request` and can allow or deny it; exceptions deny the request. SRT supplies the mechanism, while the embedder supplies the policy. Certificate-pinned and mTLS clients may require opaque tunnels, which bypass request inspection. [configuration schema](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/sandbox-config.ts)

Credential masking can give a child a placeholder and substitute the real value at the proxy only for that credential’s permitted hosts. This avoids handing the raw credential to generated code. It still authorizes actions at those hosts, so it does not prevent an abusive API call using the credential. (inference) [credential implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/credential-sentinel.ts)

**The limits are material, especially for a personal agent.**

- **A patched network escape existed.** Versions below 0.0.16 failed to enforce network isolation when no allowed domains were configured—the configuration Jezo’s present design most closely resembles. [Anthropic advisory, CVE-2025-66479](https://github.com/anthropics/sandbox-runtime/security/advisories/GHSA-9gqj-5w7c-vx47)
- **Hardening is still active.** September releases fixed filesystem deny precedence, symlink and rename handling, and allowed-host resolution to sensitive addresses. This supports using a current pinned release and maintaining updates. (inference) [release history](https://github.com/anthropics/sandbox-runtime/releases)
- **Linux can lose IPC isolation.** Missing seccomp produces a warning that Unix-socket access is unrestricted. Host sockets can provide an exit even when direct internet connections are blocked. [Linux implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/linux-sandbox-utils.ts)
- **macOS compatibility switches widen authority.** `allowAppleEvents` permits launching applications outside the sandbox; `enableWeakerNetworkIsolation` opens access to `trustd` with an acknowledged exfiltration risk. [macOS implementation](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/macos-sandbox-utils.ts)
- **Windows has explicit limitations.** System DNS resolution is not fenced; per-user tool installs often need additional read grants; per-command read/write *grants* are unsupported; some certificate-revocation checks fail behind the fence. Thus “blocked outbound TCP” is not a guarantee that no information leaves. [Windows limitations](https://github.com/anthropics/sandbox-runtime#known-limitations)
- **The wrapper does not contain its host.** Pi, Jezo’s main process, in-process file tools and extensions remain outside a shell-only sandbox. Pi documents this distinction. [Pi security documentation](https://github.com/earendil-works/pi/blob/v0.99.1/packages/coding-agent/docs/security.md)

**Codex provides a useful reference implementation, but is a less natural library dependency.** Its current local sandbox uses Seatbelt on macOS and **bubblewrap plus seccomp on Linux/WSL2**. The older description “Codex uses Landlock on Linux” is incomplete as of this date: its Linux README rejects legacy Landlock for filesystem-restricted policies because it cannot isolate app-server Unix sockets. [Codex Linux implementation](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md)

On native Windows, Codex prefers an `elevated` sandbox using dedicated low-privilege accounts, filesystem permissions and firewall rules. Its `unelevated` fallback uses a restricted token derived from the current user and environment-level offline controls; OpenAI documents it as weaker. Both normally use a private desktop. [Windows sandbox documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox)

Codex also has a local HTTP/SOCKS network proxy with domain policy and a “limited” mode intended for read-only access. Its documentation distinguishes HTTP method restrictions from opaque tunnels; merely limiting methods cannot establish that a request carries no private information. (inference) [network proxy](https://github.com/openai/codex/blob/main/codex-rs/network-proxy/README.md)

Jezo could invoke `codex sandbox` or reuse its Rust components, but would then maintain a subprocess dependency or native integration unrelated to its chosen agent SDK. SRT exposes the Node integration Jezo already needs. (inference)

**Gemini CLI also separates approvals from sandboxing.** Its documented sandbox choices include macOS Seatbelt, Docker/Podman, native Windows, gVisor and experimental LXC. [original research](https://www.accomplish.ai/blog/beltdown-escaping-the-claude-code-sandbox/) | Sandboxing bash leaves harness subprocesses as a separate attack surface. |
| **Codex, Overpatch and Heapjack, 2026** | One flaw widened patch permissions; another exposed an authorization token in a shared JavaScript heap, enabling privileged host requests. Researchers identify CLI 0.149.0 and desktop build 26.818.21641 as fixes. [original research](https://www.accomplish.ai/blog/escaping-the-openai-codex-sandbox-twice/) | Put policy and broker secrets outside model-executable contexts. |

OpenClaw research also specifically studies indirect injection, memory poisoning, unsafe tool invocation and exfiltration across personal-agent workflows. This supports treating remembered outside instructions as an ongoing threat, rather than one confined to the original email-reading turn. (inference) [Google Research publication](https://research.google/pubs/openclaw-in-the-wild-security-analysis-of-autonomous-agents/)

**A sandbox is proportionate for Jezo when it protects against outside-induced actions.** The owner’s CLI can remain trusted; an invocation whose arguments were generated after reading a hostile calendar invitation has different provenance. Restricting that invocation’s ambient authority implements “guard the exits.” It need not prohibit the owner from running the same program directly or explicitly granting wider access. (inference)

The relevant exits are:

| Exit | Example | Appropriate boundary |
|---|---|---|
| **Direct network** | Generated code sends notes or tokens with `curl`, Python, Node, SSH or another client. | OS-enforced network routing and external destination policy. Blocking a binary name is insufficient. (inference) |
| **Allowed service** | Uploading notes to an attacker-controlled repository or sending them through the owner’s email account. | Request-level destination, operation and recipient authorization. A domain grant alone is insufficient. (inference) |
| **DNS** | Private bytes encoded into a hostname query. | Controlled resolver behavior. Windows SRT explicitly documents this remaining channel. [limitation](https://github.com/anthropics/sandbox-runtime#known-limitations) |
| **Persistent host changes** | Writing shell rc files, SSH configuration, launch agents, executables or application settings. | Filesystem write boundary around workspace and dedicated tool state. (inference) |
| **Local service / IPC** | Asking Docker, an application, a credential service or a host helper to perform the action. | Socket, Mach/XPC, application-launch and broker restrictions. SRT exposes relevant controls. [schema](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/sandbox-config.ts) |
| **Later execution of workspace code** | The agent edits an extension or hook that Jezo subsequently loads in its main process. | Ensure agent-writable executable content is subsequently run under the same boundary. (inference) |
| **Another Jezo tool** | A future email-send tool or export operation transmits the same data. | Apply exit authorization to all outbound tools, not only bash. (inference) |

The current loader’s explicit extension factories already help with the later-execution problem. Preserve that property when adding plugins: a “skill + CLI” can execute inside the runner; an unrestricted Node extension loaded in Electron’s main process has a different authority level. (inference) [current loader](/Users/tim/LocalData/coding/2026/Projects/12_jezo/Jezo/src/main/agent/host.ts:246)

A filesystem fence that blocks `~/.zshrc` addresses persistence after injection. A fence that blocks unrelated credential files addresses harvesting. A broad prohibition on Python, package managers or owner-written scripts merely because they are powerful would conflict with Jezo’s principles without necessarily closing an exit. (inference)

Undo remains the right safety net for ordinary workspace mistakes. It cannot retract a disclosed secret or prevent the next unsandboxed process from executing a modified startup file. That makes filesystem scope, outbound authorization and reliable workspace undo complementary requirements. (inference)

**The options compare as follows.** This table evaluates hypothetical Jezo implementations; protection, effort and user-experience judgments are **(inference)**, based on the mechanisms above.

| Option | What it stops | What remains exposed | Compatibility and effort | Non-technical experience |
|---|---|---|---|---|
| **(a) Bash, no sandbox** | Nothing beyond host permissions and checks in individual tools. | Network exfiltration, unrelated-file access, host persistence and bypass of Jezo’s write checks. | Smallest executor change; undo still needs work. Native CLI compatibility is highest. | Smooth until something goes wrong; recovery can extend beyond Jezo. |
| **(b) Filesystem sandbox only** | Writes outside approved roots; credential harvesting if reads are also scoped. | Anything the agent can read or already knows can leave over unrestricted network. Local IPC may provide another route. | Moderate on macOS/Linux; Windows needs a real backend and installer. Many CLIs work with redirected state directories. | Few prompts, but a privacy promise would exceed the protection supplied. |
| **(c) Filesystem + external proxy + approved domains** | Most direct uploads to arbitrary internet destinations and most host persistence. | Abuse of allowed services, wildcard/DNS channels, opaque payloads and privileged host tools outside the runner. | SRT supplies much of the machinery. Packaging, CLI compatibility and policy lifecycle are the substantial work. Windows remains less mature. | Approve a connection once; routine work continues. Unexpected destinations produce a connection/setup explanation. |
| **(d) (c) + outgoing-content checks** | Adds detection of unauthorized uploads and sensitive request contents, where traffic is visible. | Encoding, summaries and allowed API operations can defeat generic content matching. Opaque TLS/SOCKS paths escape inspection. | High effort if generalized across arbitrary CLIs. TLS interception adds certificate compatibility work. | Can be good when checks understand the operation; generic detectors create unexplained blocks. |
| **(e) Offline general shell + capability-scoped integration runners/broker** | Separates arbitrary computation from authority to use accounts, recipients and remote operations. Credentials can remain outside generated code. | Authorized APIs still disclose whatever their granted operations permit; broker correctness matters. | More design than (c), but policies belong to plugins and connections instead of a universal shell parser. Can use SRT now and a VM backend later. | Local work proceeds freely; users grant recognizable connection abilities and review consequential outward actions. |

**Network-dependent CLIs must be part of the design from the start.** An offline-only shell would support parsing and generating local iCalendar files, but would still fail the maintainer’s Canvas/network-CLI use case. Jezo needs to establish the actual CLI’s endpoints, authentication and write behavior; the brief does not identify those implementations. (inference)

Common compatibility cases should be handled explicitly:

- **`~/.config` and caches:** give tools a dedicated home/config/cache tree, preferably under the owned workspace where it represents persistent user state. Grant particular paths when a CLI cannot be redirected. Avoid granting the whole real home for convenience. (inference)
- **Package installation:** allow installation into the tool environment with the required registry/CDN destinations. Installation scripts inherit the runner’s limits. A runtime’s broad development allowlist should not automatically become Jezo’s policy. (inference)
- **`brew` and machine-wide installation:** these intentionally affect locations outside the ordinary agent workspace. Put provisioning in a GUI installation action with a defined package operation, rather than granting every generated command permanent host write access. (inference)
- **Native calendar and desktop CLIs:** EventKit, AppleScript, browser automation and keychain integrations can require IPC beyond simple file/network access. Evaluate each connection; enabling SRT’s general Apple Events escape is too broad for routine use. (inference) [SRT macOS controls](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/macos-sandbox-utils.ts)
- **VM/container backends:** Linux-compatible Canvas and iCalendar tools can be packaged there, but host macOS binaries cannot simply be executed inside the Linux guest. This follows from the documented guest architecture. (inference) [Gondolin](https://github.com/earendil-works/gondolin), [Apple Containerization](https://github.com/apple/containerization)

**My recommendation is (c) as the first delivery, with (e) as its architecture.** Add narrowly defined request checks from (d) for outward writes and uploads. Avoid claiming that a domain allowlist prevents all exfiltration, and avoid making a probabilistic privacy classifier the component that decides whether isolation exists. (inference)

Concrete first steps:

1. **Create one execution service independent of Pi.** Its contract should cover policy, command, cwd, clean environment, streaming output, cancellation, exit status and cleanup. Implement it with a current pinned SRT release—0.0.78 is today’s repository release—behind an interface that can later support Gondolin or a Windows backend. (inference) [release](https://github.com/anthropics/sandbox-runtime/releases/tag/v0.0.78)

2. **Wire it through `BashOperations`.** In `createTools()`, construct `createBashToolDefinition(root, { operations: runner, exposeSessionEnvironment: false })`; activate `bash` through the existing tool list. Keep the current custom read/write/edit definitions. Treat any sandbox-start failure as a failed tool call, never an ordinary-bash retry. (inference) [Pi bash API](https://github.com/earendil-works/pi/blob/v0.99.1/packages/coding-agent/src/core/tools/bash.ts)

3. **Separate local and connection authority.** General bash gets offline execution. A connection runner receives the approved policy for that connection. Do not derive authority by searching the command for a skill name, and do not union every installed skill’s domains into one universal policy. An agent can name any installed skill; the meaningful boundary is what the selected execution context can actually reach. (inference)

4. **Keep granted policy outside agent-writable execution state.** Skill text may remain editable as Jezo intends. Effective connection grants must be changed through an owner-controlled GUI operation, rather than by editing the same `SKILL.md` the agent can modify. The policy store should fit Jezo’s distinction between workspace data and per-machine settings. (inference) [workspace and settings design](/Users/tim/LocalData/coding/2026/Projects/12_jezo/Jezo/docs/design/backend.md)

5. **Give each connected CLI a documented envelope.** Include exact domains/ports, filesystem roots, credential scope, required IPC, supported shell/runtime and remote operation classes. Prefer host-side credential injection. Start with one Canvas CLI and one calendar CLI, so the design is proven against actual integrations. (inference)

6. **Complete shell undo and post-write checks before general shell mutation ships.** Capture creations, deletions and changes with run attribution; retain the existing “do not overwrite later user edits” rule. A simple whole-workspace before/after diff cannot distinguish simultaneous GUI writes. Staging and committing changes through the write service is one solution; a mediated filesystem is another. Choose this deliberately rather than treating watcher events as attribution. (inference) [undo requirements](/Users/tim/LocalData/coding/2026/Projects/12_jezo/Jezo/docs/design/undo.md)

7. **Package and verify the runtime as part of Jezo.** Ship `rg` and required helpers at known paths; a GUI-launched Electron process cannot rely on a developer’s shell setup. LobeHub’s Windows code specifically handles helpers inside `app.asar` and per-user install locations that the sandbox account cannot read. (inference) [Pi GUI PATH issue](https://pi.dev/packages/pi-sandbox), [LobeHub helper staging](https://github.com/lobehub/lobehub/blob/canary/packages/device-sandbox/src/srt.ts)

A proposed policy needs at least these fields. This is Jezo’s policy model, not an assertion that Pi already supplies them. (inference)

| Policy area | Required information |
|---|---|
| Filesystem | Readable imports/tool directories; writable workspace/tool state/scratch; protected sessions and host-executed files. |
| Network | Exact destinations and ports; DNS handling; proxy implementation; permitted protocols. |
| Credentials | Credential identifier; eligible connection; allowed injection hosts; preferably API scope. |
| Remote actions | Allowed read operations; separately authorized uploads, sends, deletes and other consequential writes. |
| IPC | Specific required services or sockets, with an explanation of their authority. |
| Failure | Refuse execution when the promised boundary is unavailable. |
| Lifecycle | Per-run identity, active subprocess ownership, cleanup and policy concurrency. |

The SRT configuration should begin with empty network access, scoped filesystem rules and compatibility escape switches disabled. On macOS, use absolute, resolved paths rather than relying on `.` or inherited shell cwd. On Linux, reject deployment if required socket isolation is missing. On Windows, account for the documented DNS limitation before making a no-egress claim. (inference) [configuration](https://github.com/anthropics/sandbox-runtime/blob/v0.0.78/src/sandbox/sandbox-config.ts), [Windows limits](https://github.com/anthropics/sandbox-runtime#known-limitations)

For connected HTTPS CLIs, use `tlsTerminate` plus `filterRequest` where compatible, or a dedicated API broker. Verify methods, paths, identifiers, recipients and upload intent—not just the hostname. A `GET` request can carry private data in its query, so “read-only HTTP” is not equivalent to “no disclosure.” (inference) [request-filter API](https://github.com/anthropics/sandbox-runtime/blob/main/src/sandbox/sandbox-config.ts)

**The first E2E should prove useful work and denied exits in the same run.** Use a real sandboxed CLI against controlled test services, with a malicious email/calendar fixture that asks it to upload workspace content and modify a startup file. Also test an allowed domain used for an unauthorized operation, direct connections with proxy variables removed, DNS, localhost/IPC access, a newly created protected configuration path, cancellation, missing helpers and undo with intervening GUI edits. Leave the transcript, policy, service-request log and filesystem diff as repeatable artifacts. These are proposed tests; none were run during this read-only research. (inference)

The GUI should present connection abilities in ordinary terms—“Read course deadlines,” “Update this calendar,” “Send this message”—with domains and diagnostics folded into details. Local file work should proceed without questions; consequential outward actions should receive a concrete preview unless already covered by a sufficiently specific standing grant. (inference)

**The maintainer decisions that remain are:**

- Which Canvas and iCalendar CLIs must work, and do they only read or also submit, send and delete?
- Is the initial promise protection against ordinary injection-driven exfiltration, or a stronger guarantee requiring controlled DNS and a VM boundary?
- Must plugins execute native macOS binaries, or can a Linux guest become the standard tool environment?
- Does installing a connection authorize all actions through that account, or separate reading from sending/uploading?
- Should shell changes apply immediately to the live workspace, or pass through staging to preserve validation and attribution?
- What explicit owner-controlled escape is acceptable when an integration needs broader host access?

These choices determine the policy and backend. They do not require leaving bash disabled while Jezo invents a sandbox from scratch. (inference)
