**1. How projects actually handle OAuth**

Sources were checked on **2026-09-30**. Repository links refer to the inspected default branches. Explicitly dated sources older than 2026 are marked below; undated documentation is identified as live documentation rather than assumed to be newly written.

The surveyed projects use several different arrangements: a project-owned registration with local tokens, user-created registrations, a hosted token broker, or authentication delegated to a CLI/MCP server. **OAuth client ownership and token custody are separate choices.** Home Assistant documents both locally supplied credentials and centrally registered cloud credentials; Composio likewise permits a customer-owned OAuth client while retaining the resulting tokens in Composio Cloud. [Home Assistant Application Credentials](https://developers.home-assistant.io/docs/core/platform/application_credentials/), [Composio token custody](https://docs.composio.dev/docs/security/token-custody)

**2. Google’s rules for Jezo’s published Desktop client**

**Technical treatment of the “secret”**

Google explicitly assumes installed applications **cannot keep secrets**. Its current native-app token-exchange table marks `client_secret` optional. A Desktop secret therefore cannot serve as confidential proof that a binary really is Jezo. User access and refresh tokens remain credentials that require protection. [Native-app OAuth documentation](https://developers.google.com/identity/protocols/oauth2/native-app), [Token-handling guidance](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

**Publishing credentials in open-source code is a separate policy question—and the written sources conflict.**

- Google’s OAuth overview says installed-app credentials, sometimes including a secret, are embedded in application source. [OAuth overview](https://developers.google.com/identity/protocols/oauth2)
- Its OAuth policy prohibits committing client credentials to public repositories. [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies)
- More explicitly, the **live API terms, last modified November 9, 2021—older than 2026**, include client IDs among developer credentials and say: **“Developer credentials may not be embedded in open source projects.”** [API Terms, §4(b)](https://developers.google.com/terms#section_4_prohibitions_and_confidentiality)

Thunderbird, GOA and KDE visibly publish credentials despite that wording. Pi’s example instead inserts them during release builds. Those observations establish community practice; they do **not** establish a general exemption or Google’s permission for Jezo. **(inference)** [Thunderbird source](https://github.com/thunderbird/thunderbird-desktop/blob/main/mailnews/base/src/OAuth2Providers.sys.mjs), [GOA defaults](https://github.com/GNOME/gnome-online-accounts/blob/master/meson_options.txt), [Pi release workflow](https://github.com/lucasvidela94/pi-google-services/blob/master/.github/workflows/release.yml)

**Suspension risk:** Google reserves the right to suspend API access without notice for suspected terms violations. I did not verify a rule that automatically suspends every Desktop client merely because its secret becomes public. Nevertheless, publishing the credentials creates a documented policy issue; abuse, impersonation or quota exhaustion can also affect every installation sharing that project. **(inference)** PKCE protects an intercepted authorization code; it does not stop another program from starting its own authorization using a copied client ID. [API Terms](https://developers.google.com/terms), [OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies), [PKCE/native-app specification—2017, older than 2026](https://www.rfc-editor.org/rfc/rfc8252)

**PKCE and loopback**

Google supports PKCE with `S256` and loopback redirects such as `http://127.0.0.1:<ephemeral-port>` for macOS/Linux/Windows **Desktop app** clients. The listener is local to the application; no deployed callback server is required. Loopback deprecation applies to other client types, not Desktop clients. OOB copy/paste authorization is deprecated and unsupported. [Native flow](https://developers.google.com/identity/protocols/oauth2/native-app), [Loopback migration guide—originally 2022, older than 2026](https://developers.google.com/identity/protocols/oauth2/resources/loopback-migration)

**Scopes and verification**

The relevant existing-calendar scopes are `calendar`, `calendar.readonly`, `calendar.events` and `calendar.events.readonly`. Google explicitly gives Calendar event reading as a **sensitive** use case and uses `calendar` as a sensitive-scope justification example. Ordinary existing-event read/write access belongs in the sensitive-verification discussion, rather than assuming Gmail-style restricted scope requirements. **(inference for the exact scope-by-scope mapping)** [Sensitive verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth)

Google’s public Calendar scope table does **not** label every scope’s sensitivity. It also includes narrower scopes for owned calendars, free/busy, calendar lists, public events and app-created calendars. Google says the authoritative classifications appear in Cloud Console’s Data Access screen. I did not inspect an authenticated console, so I cannot claim a fully verified classification ledger for every newer Calendar scope. [Calendar inventory](https://developers.google.com/workspace/calendar/api/auth), [Classification instructions](https://developers.google.com/identity/protocols/oauth2/scopes)

Gmail’s documentation does provide an explicit classification table:

| Classification | Gmail scopes |
|---|---|
| **Non-sensitive** | `gmail.labels`; contextual add-on action scopes such as `gmail.addons.current.message.action` and `gmail.addons.current.action.compose` |
| **Sensitive** | `gmail.send`; contextual add-on message metadata/readonly scopes |
| **Restricted** | `gmail.readonly`, `gmail.modify`, `gmail.compose`, `gmail.metadata`, `gmail.insert`, `gmail.settings.basic`, `gmail.settings.sharing`, and `https://mail.google.com/` |

Read-only mailbox access is therefore restricted; removing write access does not remove restricted-scope verification. Add-on scopes apply to contextual Workspace add-ons, not an unrestricted desktop inbox reader. [Official Gmail scope classification](https://developers.google.com/workspace/gmail/api/auth/scopes)

For a publicly distributed sensitive-scope app, verification requires accurate branding, a public application homepage, a privacy policy explaining access/use/storage/sharing, domain ownership verification, scope justification, and an English demonstration video showing consent and each scope-backed feature. Google also asks why narrower scopes are insufficient. [Verification requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)

**Unverified apps, testing and personal use**

- **Testing:** up to 100 explicitly listed test users. Their authorization expires after seven days, including refresh tokens, except for basic identity-only authorization.
- **Production but unverified:** sensitive/restricted requests show the unverified-app warning and face a **100 new-user lifetime cap**, not 100 simultaneous users.
- **Publishing is not verification:** moving out of Testing removes that specific seven-day behavior but does not grant verified status or remove the unverified-user cap. [Audience and quotas](https://support.google.com/cloud/answer/15549945?hl=en)

Google documents personal-use and internal-use verification exceptions. An application used by its author or a few personally known users can use the personal-use exception; a public downloadable application does not become personal-use merely because every installation runs on one person’s machine. **(inference)** BYO registrations explain how community tools distribute software while each owner registers a personal integration. [Verification exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification#exceptions_to_verification_requirements)

**Restricted scopes and CASA**

Restricted-scope verification and the security assessment are distinct. Google’s assessment trigger covers applications that access—or can access—restricted data **from or through a third-party server**. Assessments are repeated at least every **12 months** after approval, with possible additional review when scope/functionality changes. A strictly local Gmail client and one capable of sending mailbox content to a cloud model therefore have different assessment considerations. **(inference)** [Restricted-scope requirements](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)

Google does not charge an assessment fee itself; assessors set their fees. Its live FAQ still describes a qualifying free Tier 2 route, so “every restricted-scope application must pay a fixed fee” is unsupported. Eligibility depends on Google’s assessment tier. [Google assessment FAQ](https://support.google.com/cloud/answer/13463817?hl=en)

For a concrete vendor example, TAC Security’s live FAQ advertises annual Tier 2 Basic at **$675/application**, Premium at **$855**, and Tier 3 Enterprise at **$3,600**. The page originated before 2026; these are its displayed prices checked today, not a guaranteed quote for Jezo. Its older December 2024 PDF advertises $540, illustrating why older pricing should not be reused. [Live TAC pricing](https://tacsecurity.com/esof-appsec-ada-casa-faqs-2/), [Older 2024 PDF](https://tacsecurity.com/wp-content/uploads/2024/12/ESOF-AppSec-ADA-CASA-FAQs-2_compressed-1.pdf)

Google’s limited-use rules also apply to AI handling. The live FAQ distinguishes user-directed personalized processing from using Workspace data to train/improve generalized models. Selecting a cloud model does not erase disclosure, transfer or assessment obligations. [Google limited-use FAQ](https://support.google.com/cloud/answer/13463817?hl=en)

**Quotas, billing and shared-project costs**

Google changed Workspace API quotas beginning **May 1, 2026**. Current published figures for new projects are:

| API | Per project/minute | Per user/project/minute | Published daily billing threshold |
|---|---:|---:|---:|
| Calendar | 10,000 requests | 600 requests | 1,000,000 requests/project |
| Gmail | 1,200,000 quota units | 6,000 quota units | 80,000,000 quota units/project |

Gmail units are method-dependent; for example, sending a message costs 100 units. Older projects can retain different quotas, so the actual project console remains relevant. [Calendar quotas](https://developers.google.com/workspace/calendar/api/guides/quota), [Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota)

Standard Calendar use remains documented as **no additional cost**. Its quickstart requires a Cloud project, not a billing account. **(inference)** A normal within-quota Calendar integration can use a project without billing enabled; I did not provision a fresh project to runtime-test that. [Calendar setup](https://developers.google.com/workspace/calendar/api/quickstart/nodejs), [Pricing statement](https://developers.google.com/workspace/calendar/api/guides/quota)

The current September 2026 policy page still describes future charges above daily thresholds and billing-required quota increases, following at least **90 days’ notice**. It does not publish the eventual per-request price. Consequently, “Calendar API is free forever at any scale” is no longer supported. A project shared by all Jezo users aggregates their usage against project limits. [2026 tiering policy](https://developers.google.com/workspace/tools-safety)

**3. Microsoft identity platform**

Microsoft’s treatment is clearer: desktop applications are **public clients**, cannot keep configuration-time secrets, and do not need a client secret. Microsoft documents authorization-code flow with PKCE for desktop/mobile apps and MSAL support for Electron. Tokens can remain on the user’s machine while requests go directly to Microsoft identity and Graph endpoints. [Public-client rules](https://learn.microsoft.com/en-us/entra/identity-platform/msal-client-applications), [PKCE flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Desktop/Electron configuration](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-app-configuration)

A maintainer can register:

- A single-tenant application for one organization.
- A multitenant application for any Entra organization.
- A multitenant application accepting both organizational and **personal Microsoft accounts**, needed for Outlook.com as well as Microsoft 365. [Audience types](https://learn.microsoft.com/en-us/entra/identity-platform/single-and-multi-tenant-apps)

The application registration belongs to its home tenant. The inspected registration quickstart requires an Azure account with an active subscription and appropriate tenant role; it links a free-account signup. Current tenant-creation documentation restricts creating additional workforce tenants from free/trial tenants. Thus “no server deployment required” is supported, but “a maintainer with only a consumer Microsoft login has zero onboarding requirements” is not. [Registration prerequisites](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [Tenant creation](https://learn.microsoft.com/en-us/entra/fundamentals/create-new-tenant)

**Publisher verification** requires a verified Microsoft AI Cloud Partner Program global account, a work/school app registration, domain alignment and the necessary administrative roles. Microsoft charges **no publisher-verification fee**. Verification establishes publisher identity; it is not an audit of application safety. Risk-based consent can prevent users in other organizations from consenting to new unverified multitenant applications beyond basic sign-in/profile access. [Publisher verification requirements and cost](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview)

Delegated `Calendars.Read`, `Calendars.ReadWrite`, `Mail.Read`, `Mail.ReadWrite` and `Mail.Send` are listed as not inherently requiring administrator consent. Their application-permission equivalents require admin consent and authorize access without a signed-in user. **Tenant policies can nevertheless require admin approval for delegated access**, including through publisher-verification requirements or disabled user consent. [Graph permission reference](https://learn.microsoft.com/en-us/graph/permissions-reference), [Consent behavior](https://learn.microsoft.com/en-us/entra/identity-platform/application-consent-experience)

MSAL Node caches tokens in memory by default. Desktop persistence is an explicit integration choice; Microsoft documents MSAL Node Extensions for encrypted persistence across macOS, Windows and Linux. An MSAL dependency therefore does not, by itself, mean refresh tokens are durably stored. [MSAL Node caching](https://learn.microsoft.com/en-us/entra/msal/javascript/node/caching)

**4. Patterns that avoid a shipped registration—and their 2026 status**

| Pattern | Does it work? | What it actually avoids or changes |
|---|---|---|
| **Bring your own OAuth client** | Yes: documented by gcalcli, vdirsyncer, gogcli, Hermes, n8n and MCP servers. [gcalcli](https://github.com/insanum/gcalcli/blob/main/docs/api-auth.md), [gogcli](https://github.com/openclaw/gogcli) | Avoids a maintainer-owned shared registration and its collective quota/verification burden. It adds developer-console setup for users. Google says client creation/configuration must be performed manually in Cloud Console. [Google client-creation rule](https://developers.google.com/identity/protocols/oauth2/resources/best-practices) |
| **Tiny token-exchange/refresh proxy** | Yes: Nabu Casa, Raycast and the Gemini Workspace broker demonstrate it. [Nabu Casa code](https://github.com/NabuCasa/hass-nabucasa/blob/master/hass_nabucasa/account_link.py), [Raycast proxy](https://oauth.raycast.com/), [Gemini-broker client](https://github.com/mitsuhiko/agent-stuff/blob/main/skills/google-workspace/scripts/common.js) | Avoids exposing a confidential web-client secret in the application. It still requires someone’s registration and a deployed service. Tokens pass through the broker operator—**Nabu Casa, Raycast Technologies, or the Google Gemini Workspace broker**, respectively. It need not proxy calendar/email bodies, but token custody/transit already matters under Jezo’s constraint. |
| **Device-code flow** | Microsoft supports it. Google supports it only for an explicitly limited scope list, which currently lacks Gmail and Calendar; supported Google Drive scopes include `drive.file` and `drive.appdata`. [Microsoft flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-device-code), [Google allowed scopes](https://developers.google.com/identity/protocols/oauth2/limited-input-device#allowedscopes) | Avoids a callback listener, **not application registration**: both require a client ID. It therefore is not a client-free general Google Calendar/Gmail solution. |
| **Google app password + IMAP/SMTP** | Still documented. Requires 2-Step Verification; unavailable in some organizational/security-key-only setups and with Advanced Protection. Changing the account password revokes app passwords. Hermes documents it for email-only use. [Google app passwords](https://support.google.com/accounts/answer/185833?hl=en), [Hermes email alternative](https://hermes-agent.nousresearch.com/docs/user-guide/skills/google-workspace) | Avoids an OAuth registration for supported mail access. The local application receives a reusable mail credential. It does not grant Calendar API/CalDAV access. |
| **Microsoft app password + IMAP** | Not a general Microsoft 365 workaround: Exchange Online removed Basic authentication for IMAP/POP and other affected protocols, including app-password use through those protocols. The retirement took effect before 2026; the live documentation retains that rule. [Exchange Online Basic-auth policy](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online) | Microsoft IMAP/SMTP can use OAuth, but that brings application registration back. SMTP-specific legacy exceptions do not provide calendar access or a general mail-reading fallback. [Microsoft protocol OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth) |
| **Google Calendar secret iCal address** | Yes. Google documents it for a **read-only view of one calendar**, with reset/revocation by replacing the address. Workspace administrators can make it unavailable. [Google instructions](https://support.google.com/calendar/answer/37648?hl=en) | Avoids OAuth completely. The URL itself is a bearer credential: anyone possessing it can retrieve that calendar feed. Direct local fetching introduces no connector intermediary. It cannot create/update events or read Gmail. |
| **Google CalDAV** | Yes, but Google’s current CalDAV endpoint requires **HTTPS plus OAuth 2.0**. Basic authentication is rejected with `401`, including attempts to substitute an app password. CalDAV shares Calendar API quota limits. [CalDAV developer guide](https://developers.google.com/workspace/calendar/caldav/v2/guide) | Provides a different calendar protocol, not an escape from Google OAuth registration and tokens. |
| **Generic IMAP/CalDAV with provider passwords** | Works only where the particular provider still supports that authentication. vdirsyncer supports ordinary Basic/Digest CalDAV alongside its Google-specific OAuth connector. [vdirsyncer configuration](https://vdirsyncer.pimutils.org/en/stable/config.html) | Avoids OAuth for those providers. That support cannot be generalized to Google CalDAV or Microsoft 365. |

**(inference)** Across these patterns, registration ownership determines branding, consent and quota responsibility; token custody determines who can act on the account; model routing determines who receives retrieved content. A connector’s OAuth consent grants provider access, but does not implement Jezo’s checks on agent-triggered email sends, attendee invitations, sharing changes or irreversible actions. Those remain a separate action boundary. [Google OAuth flow](https://developers.google.com/identity/protocols/oauth2), [Microsoft delegated permissions](https://learn.microsoft.com/en-us/graph/permissions-reference), [Composio custody distinction](https://docs.composio.dev/docs/security/token-custody)
